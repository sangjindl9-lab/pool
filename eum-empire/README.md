# EUM BUSINESS EMPIRE 3D

생산·유통·판매·투자·기업 경쟁을 다루는 경영 시뮬레이션입니다. TypeScript + Three.js(3D) + React(UI)로 만든 독자 게임이며, 외부 유료 API나 서버 없이 브라우저에서 싱글플레이로 동작합니다. 저장은 브라우저 IndexedDB에 합니다.

> 이 폴더는 저장소의 기존 프로젝트(착공계 판매 서버, 상위 폴더)와 완전히 독립되어 있습니다. 기존 파일은 수정하지 않았습니다.

## 실행·빌드

필요: Node.js 20 이상(22에서 확인).

```bash
cd eum-empire
npm ci            # 의존성 설치(.npmrc 의 legacy-peer-deps 사용)
npm run dev       # 개발 서버 http://localhost:5173
npm test          # 자동 테스트(vitest)
npm run build     # 타입 검사 + 배포용 빌드(dist/)
npm run preview   # 빌드 결과 미리보기
npm run bench     # 경제 엔진 성능 측정
```

`.npmrc`의 `legacy-peer-deps=true`는 npm 10의 peer 의존성 해석 오류(`Cannot read properties of null (reading 'edgesOut')`)를 피하기 위한 설정입니다.

고정 버전(2026-11 기준, 출시 2주 이상 지난 안정판): three 0.186.1, react/react-dom 19.2.9, vite 8.3.4, @vitejs/plugin-react 6.1.2, vitest 5.0.5, typescript 6.0.3. `package-lock.json`이 함께 커밋되어 있습니다.

### Windows 설치형으로 가는 길
`vite.config.ts`의 `base: './'`로 빌드 결과가 상대 경로만 사용하고, 서버·네트워크 의존이 없으며 저장도 IndexedDB(Electron/Tauri 웹뷰에서 그대로 동작)라서 `dist/`를 Tauri 또는 Electron 셸에 그대로 넣을 수 있습니다. 셸 자체(Tauri/Electron 설정, 설치 파일 생성)는 아직 추가하지 않았습니다.

## 게임 구성

| 영역 | 내용 |
|---|---|
| 모드 | 튜토리얼(부지 선택→소매점 건설→빵 구매 계약→가격 설정→첫 매출→월말 결산, 실제 행동 완료 시 다음 단계), 자유 경영(초기 자본·난이도·시드 선택, 경쟁사 3곳, 목표 4개) |
| 도시 | 48×48칸, 6칸마다 도로. 상업·주거·공업·농업 구역, 16개 지역(동). 시드로 결정적 생성 |
| 건물 | 소매점, 물류센터, 밀 농장, 제분소, 제빵공장, 목화 농장, 방직공장, 봉제공장, 본사 |
| 공급망 | 밀 → 밀가루 → 빵 → 소매점 / 원면 → 원단 → 의류 → 소매점 |
| 외부 시장 | 공급자 8곳(밀, 밀가루, 빵 2, 원면, 원단, 의류 2), 매입처 6곳. 모두 유한 재고·하루 능력 보유, 모든 회사가 같은 재고를 나눠 씀 |
| 경쟁사 | 알뜰유통(저가·대량), 프레스티지(고품질·고마진), 한결산업(수직계열화) |
| 목표 | 3개월 연속 흑자, 빵 점유율 30%, 밀→밀가루→빵→매장 자체 공급망, 기업가치 20억원 |

### 플레이어가 고민하게 되는 선택
- **매입 vs 직접 생산**: 외부 빵 도매가 ~1,750원(재고 부족 시 최대 +35%) vs 제빵공장 원가(밀가루 + 고정비가 큰 가공비). 공장은 가동률이 높아야 유리합니다.
- **저가 대량 vs 고품질 고마진**: 가격 탄력성·지역별 품질 선호가 달라 입지에 따라 정답이 다릅니다.
- **중심 상권 임대료 vs 외곽**: 지가는 중심부가 외곽의 약 10배. 임차(월 땅값의 2.5%)와 매입(토지 자산, 현금 묶임) 선택.
- **설비 vs 마케팅·연구**: 브랜드 인지도(매력도 최대 +60%)와 품질 연구(+8/단계).
- **현금 vs 대출**: 대출 한도·금리는 순자산·담보·부채비율로 결정. 현금이 30일 연속 음수면 파산.

## 경제 계산(모든 계수는 `src/engine/data/*.ts`)

### 하루 처리 순서(고정, `src/engine/sim.ts` `advanceDay`)
1. 건설 진행·완공
2. 외부 공급자 재고 보충, 매입처 재고 소비
3. **배송 도착**: 운송 중 → 구매자 재고(외상이면 이때 지급), 외부 매입처 도착분은 매출·매출원가 인식
4. **생산**: 원재료 차감 → 완제품 입고, 가공비(생산 인건비·전력비) 자본화
5. **계약 출하**: 공급자 재고 → 운송 중(Shipment), 매입 대금·운송비 지급
6. **소매 판매**: 수요 배분 → 재고 차감 → 매출·매출원가
7. 일일 고정비(인건비·임대료·유지비·전력비), 마케팅, 당좌대월 이자
8. 브랜드 인지도·연구 완료
9. 경쟁사 AI 판단(효과는 다음 날부터)
10. 지급능력 검사·파산 판정
11. 월말이면 감가상각, 대출 이자·원금 상환, 월 결산
12. 목표·튜토리얼 판정, 날짜 +1

각 배송은 출하 시 한 번 생성되고 도착 시 한 번 처리된 뒤 목록에서 사라지므로 재고가 중복 생성되지 않습니다. 플레이어 명령은 날짜 사이에만 적용됩니다.

### 시간
- 달력: 1개월 = 30일, 1년 = 12개월(2027년 1월 1일 시작). 게임 날짜와 실제 시간은 무관합니다.
- 1배속 = 1.2초에 하루, 2배속·4배속은 같은 하루 처리를 더 자주 호출할 뿐입니다(`src/game/clock.ts`). 한 프레임에 최대 4일까지만 처리합니다.

### 화폐·수량 규칙(`src/engine/money.ts`)
- 금액은 **원 단위 정수**. 비율 계산 결과는 반올림(0.5는 0에서 먼 쪽).
- 수량은 정수. 생산·출하·판매 가능량은 내림.
- 재고는 수량 + 총원가(이동평균). 일부 출고 시 원가를 비례 반올림하고, 전량 출고 시 남은 원가를 모두 가져가 원가가 보존됩니다.

### 수요와 판매(`src/engine/demand.ts`)
1. 지역 총수요 = 인구 × 1인당 수요 × 소득지수^소득탄력성. 소수점은 지역별로 이월 누적해 정수화.
2. 매장 매력도 = `exp(-거리/9)` × `(기준가/가격)^(가격탄력성×지역 가격민감도)` × `exp(품질중요도×지역 품질선호×(품질-50)/50)` × `(1 + 0.6×지역 브랜드선호×인지도/100)` × 서비스 배수(0.82/1.0/1.14).
3. 지역 수요를 매장들과 **외부 선택지**(시외 구매·구매 포기, 빵 0.55·의류 0.7)에 매력도 비율로 정수 배분(최대 잔여법).
4. 매장 판매량 = min(배분 수요, 재고). 품절로 못 판 수요의 55%는 재고가 남은 다른 매장으로 이동(거리 감쇠 12칸, 일부는 다시 외부 선택지로 빠짐), 나머지는 소멸.
5. 보장: 판매량 ≤ 재고, 총판매 ≤ 지역 총수요. 자기 가격을 올리면 자기 매력도만 줄어 판매가 늘지 않습니다. 경쟁사 가격 인하는 내 매력도 비중을 낮춥니다.

### 생산(`src/engine/production.ts`)
- 배치 수 = min(⌊하루 최대 배치 × 가동률⌋, ⌊원재료/필요량⌋, ⌊빈 공간/순증 수량⌋). 막힌 이유(원재료·공간·가동률)를 기록합니다.
- 생산 인건비 = 인원 × 90,000원 × (0.4 + 0.6 × 가동률), 전력비 = 기준 × (0.2 + 0.8 × 실제 배치/최대 배치).
- 생산이 있으면 재료 원가 + 그날 가공비가 제품 원가가 되고(자본화), 생산이 0이면 가공비는 당기 비용.
- 품질 = 투입 품질 × 0.5 + 기술 품질 × 0.5 (기술 품질 = 45 + 연구 단계 × 8, 농장은 50 + 단계 × 8).

### 공급 계약·운송(`src/engine/contracts.ts`)
- 항목: 공급자·구매자, 상품, 1회 수량, 주기, 운송 소요일, 결제 시점(출하 시 / 도착 시 외상), 부족 시 처리(부분 출하 / 전량 대기), 30일 이내 해지 위약금(1회분의 20%).
- 운송 소요일 = 1 + ⌊거리(맨해튼, 칸)/28⌋. 운송비 = 트럭 수 × 20,000원 + 수량 × 상품별 칸당 운임 × 거리(자사 물류센터 출발이면 거리 운임 30% 할인).
- 외부 공급자 단가 = 기준가 × (1 + 0.35 × (1 − 재고비율)), 트럭 2대분 이상 5%·5대분 이상 9% 할인. 매입처 단가 = 기준가 × (1 − 0.35 × 재고비율).
- 구매자 공간이 부족하면 (빈 공간 − 이미 오는 중인 수량)만큼만 출하. 현금이 부족하면 살 수 있는 만큼만 출하하고, 10회 연속 실패 시 자동 해지.
- 자사 건물 간 이동은 원가 그대로 이전(대금 없음). 그래서 공장 손익에는 비용만 보이고 이익은 판매처에서 나타납니다.

### 회계(`src/engine/ledger.ts`)
- 회사마다 복식부기 원장. 모든 금액 변동은 `postEntry` 하나로만 일어나며, 대차 합이 0이 아니거나 금액이 정수가 아니면 예외가 납니다. 현금이 움직이는 분개는 영업·투자·재무 현금흐름 구분이 필수입니다.
- 계정: 현금, 재고자산, 운송 중 재고, 토지, 건물·설비, 감가상각누계액, 외상매입금, 차입금, 자본금, 매출, 영업외수익, 매출원가, 인건비, 임대료, 운송비, 마케팅비, 유지비, 전력비, 감가상각비, 이자비용, 연구개발비, 영업외손실.
- 매입: 현금↓ 재고(운송 중)↑ — 비용 아님. 판매 시에만 매출원가.
- 건설: 현금↓ 건물↑, 토지 매입: 현금↓ 토지↑ — 비용 아님. 감가상각은 완공 후 월말에 정액(소매점 10년, 공장 15년, 농장 20년).
- 대출 실행: 현금↑ 차입금↑ — 수익 아님. 원금 상환: 차입금↓ 현금↓ — 비용 아님. 이자만 비용.
- 화면의 손익계산서·현금흐름·재무상태표·건물별 손익은 모두 이 원장의 월별 집계에서 나옵니다.

### 대출·파산(`src/engine/finance.ts`)
- 한도 = 순자산 × 0.6 + (토지 + 건물 장부가) × 0.5 − 기존 대출. 금리 = 5.5% + 8% × 부채/자산 (+ 난이도 보정). 기간 12/24/36/60개월, 매달 원금 균등 + 이자.
- 현금이 음수면 연 24% 당좌대월 이자. 30일 연속 음수면 파산(플레이어는 게임 종료, AI는 청산 후 퇴출). 1·10·20·25·28일째 경고.
- 대응 수단: 추가 대출, 건물 매각(건물 장부가 65%, 토지 90% 회수, 재고 원가 50%), 계약 축소, 마케팅 중단, 가동률 조정.

### 경쟁사 AI(`src/engine/ai.ts`)
- 난이도별 5~10일마다 시장을 평가. 플레이어와 같은 `applyCommand`만 사용하므로 현금·대출 한도·배치·공급자 재고·생산능력 제약이 똑같이 적용됩니다.
- 행동: 신규 매장·공장 건설(입지 점수 = 상권 수요 ÷ 경쟁 밀도 − 임대료), 가격 조정(지난 기간 실제 이익을 비교하며 4%씩 탐색, 품절이면 인상·재고 과다면 인하), 조달처 변경(자사 공장·물류센터가 준비되면 전환), 계약 수량 조정(판매가 아닌 수요 기준), 공장 가동률 조정·잉여 외부 판매, 마케팅 예산(매출의 1~3.5%), 운영자금 차입·조기상환, 3개월 연속 적자 매장 폐점.
- 직전 달 회사 전체가 영업적자면 확장을 멈춥니다. 주요 행동은 하단 [경쟁사 뉴스]와 [경쟁사] 화면에 표시됩니다.

### 문제 진단(`src/engine/diagnostics.ts`)
"공급 계약 없음", "품절로 판매 기회 손실", "공급자 재고 부족", "경쟁사보다 높은 가격", "품질 열세", "판매가가 원가보다 낮음", "낮은 상권 수요", "과도한 운송비", "임대료 부담", "재고 과다", "원재료 부족", "보관 공간 부족", "출하 계약 없음"을 실제 기록에서 판정하고, 각 항목에서 해결 화면(가격·공급망·시장)으로 이동합니다.

```jsonc
    "market"(상품별 60일 판매 통계), "demandCarry"(수요 이월분), "objectives", "tutorial", "gameOver", "news", "nextId"
  }
}
```

- IndexedDB `eum-empire` / `saves`: 자동 저장 1개(월말, 설정에서 끔 가능) + 수동 슬롯 5개. 파일 내보내기·가져오기(.json).
- 불러오기 검사: JSON 형식 → 포맷 표시 → 버전(더 새 버전은 거부, 이전 버전은 `MIGRATIONS`로 단계 변환) → 체크섬(불일치 시 경고 후 계속) → 구조 검증(필수 필드, 지도 크기, 회사별 대차 합 0, 재고 수량 정수). 손상 시 이유를 표시하고 불러오지 않습니다.
- 환경설정(효과음, 음량, 그림자, 장식 차량 수, 자동 저장, 성능 표시)은 localStorage에 따로 저장되며 경제 상태와 무관합니다.

장식(차량·나무·주택)은 렌더러 전용 난수로 만들어 경제 상태에 영향을 주지 않습니다. 화면의 흰 짐칸 트럭(회사 색 운전석)은 `state.shipments`의 출하일·도착일로 위치를 계산하는 **실제 배송**이고, 도로를 도는 작은 승용차는 실제 시간으로만 움직이는 **장식 차량**입니다.

### 성능 측정(측정한 값만 기재)
- **경제 엔진**(`npm run bench`, Node 22, 이 컨테이너): 건물 27개(회사 4곳, 플레이어 매장 12개)·계약 46건, 1년 360일 처리 361ms → **평균 1.0ms/일, 최악 12.3ms/일**. 4배속(초당 약 3.3일)에서 프레임당 경제 계산 부담이 작아 Web Worker 분리는 아직 하지 않았습니다(엔진은 DOM 의존이 없어 필요 시 그대로 Worker로 옮길 수 있음).
- **렌더링**: 이 컨테이너에는 GPU가 없어 Chromium이 SwiftShader(CPU 소프트웨어 GL, 4코어)로 그립니다. 1280×720, 건물 18개·배송 19건에서 그림자 켬 2.6 FPS(드로우콜 339) / 그림자 끔 4.9 FPS(드로우콜 134)를 측정했습니다. 이는 소프트웨어 렌더링 수치이며 **실제 GPU가 있는 PC의 FPS는 측정하지 않았습니다**. 건물 메시를 재질별로 병합하고 바닥·장식·차량을 InstancedMesh로 그려 드로우콜을 줄였습니다. 실제 PC에서 FPS는 게임 안 [저장·설정 → 성능 정보 표시]로 확인할 수 있습니다.
